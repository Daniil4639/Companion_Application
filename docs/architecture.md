# Архитектура

## Цели

Первая архитектура должна надёжно поддерживать локальные календарь и задачи, оставаться понятной для постепенного развития и не привязывать базовую логику к LLM или MCP. Для текущего масштаба используется модульный монолит.

## Текущая основа

- **Backend:** Python и FastAPI.
- **Хранилище:** SQLite через SQLAlchemy; схема развивается миграциями Alembic.
- **Frontend:** HTML, JavaScript и CSS, раздаваемые локальным приложением.
- **Доступ:** браузерный интерфейс обращается к API на том же локальном приложении.
- **Развёртывание:** локально, для одного пользователя.

В репозитории уже есть модели событий, правила повторения, исключения отдельных повторов, DTO, API-маршруты и сервис календаря. Основные маршруты расписания находятся под `/api/schedule`, события — под `/api/events`, отдельные повторы — под `/api/events/{event_series_id}/occurrences`; проверка доступности — `/api/health`. Реализованный календарный API — начальная основа, а не утверждение о завершённой функциональности.

Frontend в текущем состоянии содержит материалы в `frontend/backups/` и референсы в `frontend/references/`. Часть резервного прототипа отображает будущие разделы, но они не считаются реализованными функциями продукта.

## Целевая структура модулей

```text
HTML / JavaScript / CSS
          │ HTTP
          ▼
      FastAPI API
          │
          ▼
 Прикладные сервисы и правила
      ┌───┴─────────┐
      ▼             ▼
  Календарь       Задачи
      │             │
      └──────┬──────┘
             ▼
       SQLite / SQLAlchemy
          Alembic migrations
```

Слои и ответственность:

- **UI** отображает данные и передаёт пользовательские действия в API. Он не содержит правил сохранения и бизнес-логики.
- **API-маршруты** проверяют входные данные, вызывают сервисы и формируют HTTP-ответы.
- **Сервисы доменов** реализуют правила календаря и задач отдельно от HTTP и UI.
- **Модели и хранилище** сохраняют состояние; изменения схемы оформляются миграциями.
- **Будущие интеграции** подключаются отдельными модулями и адаптерами, не вмешиваясь в обязательный путь работы календаря и задач.

## Данные и домены

### Календарь

В текущей модели есть серия событий с началом, окончанием, часовым поясом и описанием; повторяемость хранится отдельным правилом. Исключения позволяют отменять или переносить отдельный экземпляр события. Расписание выдаётся диапазоном дат. Контракт API следует сохранять при дальнейших изменениях, если нет явного решения его изменить.

### Задачи

Домен задач реализован независимо от событий: модель Task, DTO, TaskService, REST API /api/tasks и Kanban-вкладка. Четыре фиксированных статуса: BACKLOG → TODO → IN_PROGRESS → DONE; даты необязательны. Сервис управляет атомарными перемещениями, порядком и completed_at. Календарь отображает ту же запись задачи по её плановой дате и дедлайну, не создавая событий. Контракт и правила транзакций описаны в tasks-api.md. Чтение задач также доступно через MCP tasks_list.

## Будущие интеграции

После того как базовые сценарии работают:

- адаптеры смогут изолировать различия между локальными и облачными LLM-провайдерами;
- операции календаря, задач и лора можно будет представить как инструменты для ИИ;
- MCP уже предоставляет локальный доступ к чтению и записи поверх существующих сервисов;
- Obsidian и API базы знаний мира будут отдельными источниками/адаптерами;
- чат и маскот станут дополнительным интерфейсом, а не единственным способом использовать приложение.

MCP-сервер встроен в lifespan FastAPI: Streamable HTTP /mcp, официальный SDK 2.3.0, инструменты tasks_list, schedule_list, tasks_create, tasks_update, tasks_move, tasks_complete и schedule_create. Адаптер backend/app/mcp_adapter вызывает TaskService и CalendarService через отдельные сессии существующего get_db. Доступ ограничен localhost; MCP изменяет задачи, создаёт и редактирует обычные события и отдельные вхождения. CalendarEditingService проверяет версию снимка и запрещает неявное изменение всей серии; схема БД не меняется. Подробности — [mcp-calendar-editing.md](mcp-calendar-editing.md). Настройка, ограничения и проверка через Inspector описаны в [mcp.md](mcp.md).

## Принципы надёжности и безопасности

- Календарь и задачи должны быть доступны без ИИ и сетевого подключения.
- Изменения данных проходят через прикладные сервисы и валидацию API.
- Изменения схемы БД вносятся новыми миграциями; старые миграции не переписываются без отдельного объяснения последствий.
- По умолчанию не передавать локальные данные внешним провайдерам.
- Не добавлять авторизацию, синхронизацию между устройствами и многопользовательскую изоляцию в MVP: их необходимость не подтверждена.
- Сохранять существующие API-контракты и развивать приложение небольшими изменениями.


Изменения правил повторения планируются в services/recurrence_editing.py без доступа к БД; запись плана выполняется в общей транзакции с проверкой версии. Preview использует тот же план и общий render_schedule без записи в SQLite. Новые таблицы не требуются. Контракт: [mcp-recurrence.md](mcp-recurrence.md).
