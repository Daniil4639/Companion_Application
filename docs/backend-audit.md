# Аудит backend и план реализации Kanban

Дата: 22 октября 2026 года. Проверена текущая копия `Companion_Application`.

Это исходный отчёт до исправлений. Календарный backend затем исправлен и покрыт регрессионными тестами; актуальные правила, API и запуск описаны в [calendar-api.md](calendar-api.md). Kanban пока не реализуется.

## Вывод

Основа модульного монолита подходит для проекта. Переписывать приложение целиком не требуется. До реализации Kanban и подключения рабочего интерфейса необходимо исправить календарные исключения, обработку времени, валидацию и конфигурацию запуска.

Аудит не изменял код приложения, миграции и пользовательскую БД. Динамические проверки выполнены на SQLite в памяти, с отдельным FastAPI-приложением, реальными маршрутизаторами проекта и подменой зависимости сессии. Для проверки генерации расписания исключения отдельно добавлялись с заполненными служебными датами: это позволило проверить алгоритм после обхода известной ошибки вставки. Полный запуск приложения с пользовательской конфигурацией не выполнялся.

## Что уже сделано удачно

- Есть отдельные каталоги API, сервисов, DTO, моделей и инфраструктуры БД.
- CalendarService не импортирует FastAPI и получает AsyncSession извне.
- Сервис вызывает flush, маршруты выполняют commit; это уже позволяет объединять операции в транзакции.
- На запрос создаётся отдельная сессия; контекстный менеджер закрывает её и откатывает незавершённую транзакцию. Отсутствие явного rollback в get_db само по себе не означает утечку транзакций.
- expire_on_commit=False подходит для чтения результатов после commit в асинхронном коде.
- Для runtime-соединений SQLite включены внешние ключи.
- Правило повторения загружается через selectinload при чтении расписания.
- Ограничения положительного interval/count, взаимного исключения count/until и уникальности исключения присутствуют в БД.
- Начальная миграция успешно создаёт схему; сравнение Alembic с metadata не выявило расхождений. Её downgrade также выполнен на тестовой БД.

## Проблемы, которые нужно исправить

### 1. Новые переносы и отмены завершаются ошибкой — высокий приоритет

Источники: `backend/app/services/calendar.py:172`, `:206`; `backend/app/models/event_exception.py:73`.

При создании EventException не передаются created_at и updated_at. В модели и миграции эти поля обязательны, defaults отсутствуют. Оба HTTP-сценария воспроизведены с ответом 500 и IntegrityError по created_at.

Исправить единый способ установки служебных дат, обновление updated_at и проверки состояния исключения. Для MODIFIED нужны корректные start_at/finish_at и положительная длительность; для CANCELLED нужно согласованное представление отмены.

### 2. Переносы неправильно попадают в диапазон расписания — высокий приоритет

Источник: `backend/app/services/calendar.py:88` и `:97`.

Генерируются исходные старты внутри диапазона, исключения также выбираются по original_start_at. После применения переноса фактическое пересечение диапазона не проверяется.

Воспроизведение: повтор 22 октября перенесён на 27 октября. В выдаче за 22 октября возвращается событие с датой 27 октября; выдача за 27 октября пуста.

Исправить сборку расписания: обычные повторы с учётом исключений плюс перенесённые экземпляры, фактически пересекающие диапазон, включая переносы из-за его пределов. Устранить дубли по идентичности экземпляра `(event_series_id, original_start_at)`.

### 3. Границы и пересечения диапазона неодинаковы — высокий приоритет

Источники: `backend/app/services/recurrence.py:60`; `backend/app/services/calendar.py:237`.

Для одиночных событий используется пересечение интервалов, для повторов — старт внутри диапазона с включённой правой границей. Поэтому повтор 09:00–10:00 отсутствует в запросе 09:30–10:30, но попадает в запрос 08:00–09:00. Оба случая воспроизведены.

Принять общий диапазон `[range_start, range_end)` и условие `start_at < range_end and finish_at > range_start`. При генерации учитывать события, начавшиеся до левой границы и продолжающиеся внутри диапазона.

### 4. Часовые пояса не обрабатываются последовательно — высокий приоритет

Источники: `backend/app/models/event_series.py:49`; `backend/app/services/calendar.py:88`; `backend/app/dto/events.py:23`.

В текущем SQLite-пути DateTime(timezone=True) не сохраняет UTC-смещение. Создание события 09:00+03:00 вернуло 09:00 без смещения. Получение расписания с timezone-aware границами при наличии повторов вернуло 500; с naive-границами — 200. Поле timezone хранится, но не используется при генерации повторений. DTO допускают смешение naive и aware дат.

Предлагаемая политика: моменты времени нормализовать в UTC с явным восстановлением timezone при чтении SQLite; идентификатор зоны IANA хранить отдельно. Повторы рассчитывать в локальном времени зоны события и затем переводить в UTC. Простого удаления tzinfo недостаточно. Проверять зону и согласованность входных дат.

До реализации определить поведение несуществующего/двусмысленного времени при DST и длительности события через смену смещения. При наличии старых записей нельзя массово считать их UTC: текущий формат мог сохранить локальное время без смещения. Нужен отдельный план преобразования данных.

### 5. Нет проверки существования экземпляра — высокий приоритет

Источники: `backend/app/services/calendar.py:157` и `:193`.

Методы проверяют только наличие существующего исключения. Они не проверяют серию и принадлежность original_start_at её правилу/count/until. После исправления служебных дат можно будет записать исключение для произвольной даты существующей серии. Отсутствующая серия будет выявляться ограничением БД, а не понятной доменной ошибкой.

Проверять серию и реальное существование экземпляра до записи. Ввести отдельные ошибки «серия не найдена», «экземпляр не существует», «некорректные данные», «конфликт». Определить повторную отмену и перенос уже отменённого экземпляра.

### 6. Исключения одиночных событий игнорируются — высокий приоритет

Источник: `backend/app/services/calendar.py:245`.

Ветка без recurrence_rule сразу добавляет исходное событие, не читая исключения. Воспроизведено: одиночное событие с сохранённой отменой всё равно присутствует в расписании. Нужно либо поддержать единый механизм исключений, либо явно ограничить endpoints отдельными повторами и реализовать редактирование/удаление одиночных событий отдельно.

### 7. Валидация пропускает некорректные данные — высокий приоритет

Источники: `backend/app/dto/events.py:7`, `:19`; `backend/app/api/schedule_router.py:19`; `backend/app/api/occurrence_router.py:24`.

Подтверждено:

- finish_at == start_at при создании → 500 вместо клиентской ошибки;
- count и until одновременно → 500;
- обратный диапазон расписания → 500 из-за необработанного ValueError;
- несуществующая зона и название из пробелов → 201;
- некорректный день недели допускается DTO и вызывает KeyError в генераторе;
- DTO допускают month=13, monthday=0 и смешанные naive/aware даты.

Добавить валидацию дат, зон, названий и параметров повторения. Существенные доменные правила должны проверяться в сервисах независимо от HTTP. DTO отвечают за формат входа; FastAPI переводит доменные ошибки в HTTP: 422 для некорректного запроса, 404 для отсутствующего объекта, 409 для подтверждённого конфликта. Непредвиденные ошибки БД не следует все подряд маскировать под 409.

### 8. Конфигурация БД и миграций может расходиться — высокий приоритет

Источники: `backend/app/config/settings.py:4`; `backend/app/db/session.py:8`; `backend/app/alembic/env.py:13`; `backend/app/main.py:18`.

Runtime читает переменные окружения при импорте settings. Загрузка .env происходит только внутри Alembic, после импорта моделей и инициализации runtime engine. Если переменные не предоставлены снаружи, engine может получить None.db, а миграция — другое имя из .env. Пути к БД, alembic.ini и script_location зависят от рабочего каталога.

Ошибка миграции перехватывается, но приложение продолжает стартовать, а health всегда сообщает ok. Исправить единые настройки и абсолютные пути, валидацию конфигурации и прекращение запуска при невозможности подготовить схему. Различать проверку процесса и готовность БД. Для локального режима использовать явный loopback-адрес запуска.

### 9. CRUD неполный — необходимое расширение

Есть создание/чтение серии, расписание, перенос/отмена экземпляра. Нет обновления и удаления серии. Ответ EventResponse содержит только recurrence_rule_id, но не параметры правила; отдельного endpoint чтения этого правила нет. Этого недостаточно для полноценной формы редактирования.

Добавить минимальные операции редактирования/удаления и представление правила в ответе. Сначала определить семантику изменения всей серии и судьбу исключений. Сценарий «этот и все последующие» можно отложить, если он не нужен MVP. Удаление согласовать с RESTRICT и очисткой принадлежащего серии правила.

### 10. Транзакции и ограничения требуют усиления

Не требуется перестраивать уже работающий жизненный цикл сессии. Требуется единая транзакционная граница для HTTP и будущего MCP: одна изменяющая операция либо полностью сохраняется, либо откатывается. Низкоуровневые методы могут продолжать использовать flush.

Параллельные запросы переноса/отмены могут оба прочитать отсутствие исключения и затем столкнуться с UniqueConstraint. Это риск из анализа кода, конкурентный сценарий отдельно не запускался. Нужна согласованная стратегия конфликта/идемпотентности и тест. Добавить ограничения допустимых состояний исключений. Enum с native_enum=False не следует считать достаточной CHECK-защитой от произвольных строк при прямой записи.

### 11. Производительность и запуск интерфейса — следующий приоритет

- get_schedule выбирает все повторяющиеся серии и выполняет запрос исключений для каждой. Добавить ограничение диапазона/объёма выдачи, пакетное чтение исключений и проверить стоимость старых бесконечных серий.
- Путь к `/static` рассчитан правильно, импорт main успешен. Однако frontend_router ожидает `frontend/templates/index.html`, которого нет: шаблон находится в backups. Подключить будущий рабочий frontend и согласовать единый способ раздачи ресурсов.
- Зафиксировать зависимости и поддерживаемый Python: в каталоге не найдено pyproject.toml/requirements/lock-файла. В env.py есть синтаксис f-string, требующий Python 3.12+.
- В нескольких __init__.py написано `_all_` вместо `__all__`; убрать wildcard-импорты, print при импорте и устаревшее упоминание PyScript. Это уборка после исправления функциональности.

## Повторное использование в MCP

Существующий CalendarService можно сохранить. Создание ORM-правила сейчас выполняется в API, а проверка длительности переноса — только в маршруте. Перенести создание и доменные проверки в сервисные операции с входными структурами данных и типизированными ошибками. FastAPI и будущий MCP будут вызывать одинаковые операции, каждый со своим переводом ошибок и сериализацией.

Не нужен отдельный микросервис или обязательный универсальный repository-слой. Достаточно ясных границ сервисов, транзакций и входных/выходных контрактов. Сам MCP на этом этапе не реализуется.

## Проверки и пробелы

В репозитории не найдены тесты и конфигурация тестового набора; pytest в доступном Python не установлен. Проведены отдельные диагностические проверки через httpx ASGITransport, SQLAlchemy и Alembic, а не запуск существующего test suite. Версии среды: Python 3.13.2, SQLAlchemy 2.0.52, FastAPI 0.136.3, Pydantic 2.13.4, Alembic 1.19.1, python-dateutil 2.9.0.post0.

Проверены: создание события (201), отсутствующая серия (404), ошибочные запросы, сохранение смещения, перенос/отмена, перенос между диапазонами, пересечение левой границы, правая граница, игнорирование отмены одиночного события, upgrade/downgrade начальной миграции и сравнение metadata. Обычный Alembic env.py не запускался, чтобы не читать .env и не затронуть рабочую БД.

Нужные регрессионные тесты:

1. Указанные выше воспроизведения через API и напрямую через сервисы.
2. Daily/weekly/monthly/yearly, interval, count, until, комбинации by-фильтров, конец месяца, 29 февраля, пустой результат.
3. UTC, положительные/отрицательные смещения, нормализация идентичности экземпляра, DST gap/fold и смена зоны.
4. Перенос в диапазон/из диапазона, пересечения полуночи, повторный перенос, отмена после переноса, повторная отмена, несуществующий экземпляр.
5. Откат после ошибки, независимость сессий, конкуренция при создании исключения, сохранение данных после повторного открытия БД.
6. Чистая миграция и обновление с предыдущей схемы с сохранением данных; ограничения FK/unique/check и очистка при удалении.
7. Для Kanban — CRUD, фильтр дня, смена статуса, перенос дня, порядок карточек, возврат из завершённых, транзакционный откат.

## Что добавить для Kanban

Предложение для MVP, ещё не реализованный контракт:

- Отдельная сущность Task: UUID, title, необязательное description, planned_date типа DATE, status (`planned`, `in_progress`, `done`), created_at, updated_at. completed_at полезен для фиксации завершения. position добавлять, если нужна ручная сортировка карточек.
- День задачи — календарная дата, без преобразования полуночи в UTC. Задача не обязана занимать интервал времени и не должна наследоваться от EventSeries.
- TaskService: создание, чтение, редактирование, удаление, смена статуса, перенос на другой день; проверки и транзакции общие для всех адаптеров.
- Новые DTO и API `/api/tasks`: POST, GET со списком по дню/диапазону, GET/PATCH/DELETE по id. Специальные endpoints перемещения нужны только при реальной необходимости атомарной сортировки нескольких карточек.
- Новая Alembic-миграция таблицы tasks, ограничений и индекса по planned_date/status. Старую миграцию календаря не переписывать.
- UI: выбранный день, три колонки, создание/редактирование карточки, смена статуса и даты. Drag-and-drop можно дополнить обычными кнопками/меню.

До реализации согласовать обязательность дня (по текущему описанию — обязателен), возврат завершённых задач в работу, поведение невыполненных задач прошлого дня и необходимость ручной сортировки. Рекомендуемый старт: разрешить возврат, оставить незавершённые задачи на исходной дате до явного переноса, не вводить проекты/подзадачи/повторы задач в MVP.

## Последовательность изменений

1. Зафиксировать окружение и запуск: зависимости, настройки, пути, миграции, готовность БД. Подготовить изолированные фикстуры для проверок.
2. Зафиксировать политику времени и существующих данных; согласовать диапазоны и поведение одиночных событий/серий.
3. Исправить время, служебные даты, валидацию и доменные ошибки; добавить регрессионные тесты на подтверждённые сбои. Изменения схемы оформлять новыми миграциями.
4. Исправить алгоритм расписания и исключений, проверить границы, переносы и повторения; затем добавить недостающие update/delete и транзакционные сценарии.
5. Реализовать Task, TaskService, API и миграцию Kanban с отдельными проверками.
6. Подключить рабочий календарь и Kanban-интерфейс в согласованной палитре, проверить повседневные сценарии и перезапуск.

Критерий перехода к расширениям: календарь и задачи устойчиво работают локально, ошибки пользователя дают понятные ответы, переносы и даты не искажаются, а изменения данных проверяются независимо от HTTP. ИИ и MCP остаются последующими этапами.
