# Calendar API: запуск и правила работы

## Текущий объём

Backend поддерживает создание, чтение, список, частичное изменение и удаление серий/одиночных событий; построение расписания; перенос, отмену и восстановление экземпляра. Календарный frontend подключён на /. Независимый модуль задач и Kanban описан в tasks-api.md. Старые frontend-файлы остаются в backups. Описание интерфейса — frontend.md.

## Запуск

Проверено на Python 3.13.2. Зависимости зафиксированы в requirements.txt, зависимости проверок — в requirements-dev.txt.

Из корня Companion_Application:

```powershell
python -m pip install -r requirements.txt
python -m backend.app.main
```

Приложение по умолчанию доступно на http://127.0.0.1:8100. Интерактивная документация — /docs, OpenAPI — /openapi.json. При запуске применяются миграции; при ошибке схемы приложение не начинает обслуживать запросы. /api/health проверяет доступность таблиц календаря.

Настройки читаются из окружения и .env в корне проекта; уже заданные переменные окружения имеют приоритет:

| Переменная | Значение по умолчанию | Назначение |
|---|---|---|
| APP_HOST | 127.0.0.1 | Локальный адрес сервера |
| APP_PORT | 8100 | Порт |
| SQL_LITE_DB_NAME | companion | Имя БД без .db в корне проекта |
| DATABASE_URL | Вычисляется из имени | Переопределение: sqlite+aiosqlite:///... |
| COMPANION_LOAD_DOTENV | 1 | Значение 0 отключает чтение .env для изолированных проверок |

Относительный путь БД разрешается от корня проекта. Alembic и приложение используют один источник настроек. DATABASE_URL имеет приоритет над SQL_LITE_DB_NAME.

## Время и повторения

- Все входные моменты содержат UTC-смещение: например, 2026-10-22T09:00:00+03:00 или 2026-10-22T06:00:00Z. Даты без смещения отклоняются с 422.
- Выходные моменты нормализованы в UTC. SQLite хранит UTC без суффикса зоны; тип UTCDateTime восстанавливает UTC при чтении.
- Поле timezone — существующий идентификатор IANA, например Europe/Moscow. Оно определяет местное время повторения. Входной offset задаёт момент, который переводится в эту зону.
- Повтор «ежедневно в 09:00» сохраняет местное время при смене UTC-смещения. Продолжительность экземпляра — фиксированное прошедшее время между исходными start_at и finish_at.
- Несуществующее местное время при весеннем DST пропускается. COUNT считает реальные экземпляры. При осенней неоднозначности используется первый момент; для самого DTSTART сохраняется явно переданный момент.
- Входной момент с явным offset всегда трактуется как момент времени, а не как неуточнённое местное время.
- UNTIL включительно; одновременно count и until запрещены. В until также требуется offset.
- Дни недели: MO, TU, WE, TH, FR, SA, SU. Дни месяца: 1..31 или -31..-1. Месяцы: 1..12.
- Невозможные календарные даты пропускаются: ежемесячное событие 31-го не переносится автоматически на последнее число короткого месяца.
- Фильтры повторения могут исключить сам DTSTART; экземплярами считаются результаты правила.
- Расписание использует диапазон [range_start, range_end). Возвращаются все пересекающиеся события, включая начавшиеся раньше диапазона. Событие, заканчивающееся на левой границе, не включается.
- original_start_at — постоянная идентичность экземпляра, не меняющаяся после переноса. Эквивалентные UTC-смещения идентифицируют один экземпляр.

## Маршруты

| Метод | Путь | Результат |
|---|---|---|
| POST | /api/events | Создать серию или одиночное событие; 201 |
| GET | /api/events?limit=100&offset=0 | Список серий, включая правило повторения |
| GET | /api/events/{id} | Прочитать серию; 200 или 404 |
| PATCH | /api/events/{id} | Изменить переданные поля; 200 |
| DELETE | /api/events/{id} | Удалить серию, исключения и принадлежащее ей правило; 204 |
| GET | /api/schedule?range_start=...&range_end=... | Расписание по фактическому времени |
| POST | /api/events/{id}/occurrences/{original_start_at}/move | Перенести экземпляр; 200 |
| POST | /api/events/{id}/occurrences/{original_start_at}/cancel | Отменить экземпляр; 200 |
| POST | /api/events/{id}/occurrences/{original_start_at}/restore | Убрать исключение и восстановить исходный экземпляр; 204 |
| GET | /api/health | Готовность таблиц; 200 или 503 |

Создание:

```json
{
  "title": "Планирование",
  "description": "Разобрать расписание",
  "start_at": "2026-10-22T09:00:00+03:00",
  "finish_at": "2026-10-22T10:00:00+03:00",
  "timezone": "Europe/Moscow",
  "recurrence_rule": {
    "frequency": "weekly",
    "interval": 1,
    "by_weekday": ["TH"],
    "count": 4
  }
}
```

Для одиночного события recurrence_rule не передаётся или равен null. Ответ сохраняет прежние поля и добавляет вложенное recurrence_rule с параметрами правила.

Перенос:

```json
{
  "start_at": "2026-10-23T11:00:00+03:00",
  "finish_at": "2026-10-23T12:00:00+03:00"
}
```

Передавайте query-параметры через URL-кодирование: символ + в смещении query-параметра должен быть %2B. ISO-время с Z удобнее для адреса экземпляра.

## Изменения и исключения

PATCH меняет только явно переданные поля. description=null очищает описание; recurrence_rule=null убирает повторение. Переданный объект recurrence_rule полностью заменяет параметры правила, а не объединяет их по полям.

Изменение названия/описания серии сохраняет исключения. Если меняются время, зона или правило и исключения уже существуют, сервер отвечает 409. Явное ?reset_exceptions=true разрешает удалить все исключения этой серии и применить новое время/правило одной транзакцией. Нельзя удалять исключения автоматически при редактировании без решения пользователя.

Одиночные события используют те же move/cancel/restore. Их original_start_at равен исходному start_at.

Повторная отмена и восстановление уже исходного экземпляра идемпотентны. Перенос отменённого экземпляра восстанавливает его с новым временем. Перенос не меняет исходное правило. Отмена после переноса скрывает перенесённый экземпляр; restore возвращает его на исходное место.

Изменение «этот и все последующие», редактирование текста отдельного экземпляра и события на целый день отдельным типом пока не входят в API.

## Транзакции и будущие адаптеры

CalendarService принимает AsyncSession, проверяет доменные данные, записывает изменения и не выполняет commit. HTTP-маршруты используют общий write_transaction; в нём берётся SQLite-блокировка записи до чтения изменяемого объекта. Это предотвращает гонку между чтением и записью. Исключения сохраняются через атомарный upsert по паре (event_series_id, original_start_at).

Будущий MCP-адаптер должен вызывать те же сервисы и write_transaction. Он не должен воспроизводить проверки и SQL в своём коде. Для нескольких операций, которые должны быть атомарными, используется одна сессия и одна внешняя транзакция.

Сервисные ошибки: InvalidCalendarData, CalendarNotFound, CalendarConflict. HTTP переводит их в 422, 404 и 409. При занятой SQLite сервер отвечает 503 с Retry-After: 1. Неожиданные ошибки БД дают 500 без SQL и параметров в ответе.

Ограничения защиты от слишком больших запросов: диапазон до 366 дней, до 1000 выбранных серий, до 10000 экземпляров/исключений, до 100000 просмотренных кандидатов одной серии. Превышение возвращает 422 без молчаливого обрезания. Страница списка серий — максимум 500 элементов. interval ограничен 1000, count — 100000.

## Миграция существующих данных

Начальная миграция c1daa961f302 не изменена. Новая d2e8c4a91760 добавляет ограничения, служебные defaults и преобразование времени.

Пустая БД обновляется автоматически. Для заполненной старой БД невозможно надёжно восстановить потерянное UTC-смещение без знания прежних правил записи. Автообновление останавливается до изменений.

После остановки приложения, резервного копирования файла БД и определения смысла старых значений выберите один подход:

1. Если даты событий были местным временем их поля timezone, а служебные даты записывались на машине с зоной Europe/Moscow:

```powershell
python -m alembic -x legacy_time_policy=event_timezone -x legacy_audit_timezone=Europe/Moscow upgrade head
```

Замените legacy_audit_timezone фактической зоной прежнего сервера. Этот вариант корректен только если offsets исходных дат соответствовали зоне события. Если данные вводились с разными несогласованными offsets, сначала требуется отдельное восстановление данных.

2. Если все старые моменты, включая служебные даты, уже были UTC:

```powershell
python -m alembic -x legacy_time_policy=utc upgrade head
```

Неоднозначное или несуществующее местное время в старой БД останавливает преобразование. Ошибка ограничений/внешних ключей откатывает всю новую миграцию, включая преобразованные даты.

Downgrade новой миграции разрешён только для пустого календаря. Для заполненной БД восстановление старой версии выполняется из предварительной резервной копии, чтобы старый код не истолковал UTC как прежнее местное время.

## Тип события (category)

Модель EventSeries и API поддерживают category: default, work, entertainment, learning, health, personal, rest. При создании без поля используется default. PATCH не допускает null или неизвестное значение. Тип возвращается в списке событий и расписании, применяется ко всей серии, включая перенесённые экземпляры. Изменение только типа не требует сброса исключений.

Миграция для нового поля намеренно не создана и не применена. До работы с обновлённым календарём существующую БД необходимо обновить. Создание скрипта из корня проекта:

```powershell
python -m alembic revision --autogenerate -m "add event category"
```

В сгенерированном скрипте следует проверить, что добавляется только category, nullable=False, с server_default="default" для существующих записей. Команда создания скрипта сама схему БД не меняет. Применение после просмотра скрипта: `python -m alembic upgrade head`. Обычный запуск приложения также применяет уже созданные миграции.
