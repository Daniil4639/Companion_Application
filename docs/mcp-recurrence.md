# MCP Calendar Tools v1: повторения

Сервер предоставляет 17 инструментов. Этот этап добавляет schedule_update_recurrence, schedule_split_series, schedule_restore_occurrence, schedule_preview_change и get_user_context. Существующие инструменты и REST-контракты сохраняются; новых таблиц и миграций нет.

## Контракт правила

Правило передаётся структурированным объектом recurrence_rule, а не произвольной строкой RRULE. Поддерживается существующее подмножество: frequency (daily, weekly, monthly, yearly), interval, by_weekday (MO…SU), by_monthday, by_month и одно условие окончания — until либо count. Оба окончания одновременно запрещены. Числовые значения строгие: строки и bool вместо чисел не принимаются.

Правило заменяется **целиком**. Пропущенные параметры получают значения по умолчанию, а не наследуют старые. Чтобы поменять только окончание, возьмите правило из schedule_get, измените его и передайте полностью. Например, при переходе с COUNT на UNTIL уберите count.

DTSTART должен сам соответствовать новому правилу и не быть позже UNTIL. Если меняются дни недели и старый DTSTART больше не подходит, укажите start_at. Он трактуется как момент со смещением; IANA timezone серии сохраняется, как и фактическая продолжительность. Для изменения только будущей части используйте split, поскольку update_recurrence меняет также прошлое серии.

Все операции записи требуют expected_version из schedule_get. Проверка версии и запись происходят под одной SQLite writer reservation. Повторные/устаревшие запросы отклоняются с VERSION_CONFLICT. Это защита от повторного применения, а не возврат закэшированного успешного ответа. После потери ответа сначала перечитайте данные.

## Политики исключений

| exception_policy | Поведение |
| --- | --- |
| reject (по умолчанию) | Отказ при наличии затронутых исключений |
| preserve | Сохранение ID, отмен, фактического времени и текстов, только если все исходные времена остаются в новом правиле |
| discard | Явное удаление затронутых исключений; результат перечисляет их ID и содержит предупреждение |

Инструменты не пытаются угадать, как сопоставить старое отменённое занятие с новым днём недели. Несовместимое preserve отклоняет всю операцию. При update_recurrence затронуты все исключения. При split — только исключения с original_start_at на границе или позже; исторические сохраняются даже при discard.

## Разделение серии

schedule_split_series принимает data.original_start_at — исходное начало выбранного вхождения, даже если оно перенесено или отменено. Оно должно существовать в исходном правиле. Разделение перед самым первым вхождением отклоняется: для этого есть update_recurrence.

Историческая серия сохраняет свой ID и все исходные вхождения **до** границы. Её правило ограничивается COUNT, равным числу прошлых реальных вхождений. Новая серия получает новый ID и начинается выбранным вхождением либо указанным data.start_at. Новое начало не может быть раньше границы. Продолжительность, timezone, название, описание и категория наследуются.

- Если recurrence_rule не передан, новая серия наследует правило. При COUNT из него вычитается число прошлых исходных вхождений; отменённые вхождения тоже считаются. При UNTIL сохраняется прежний абсолютный момент окончания. Бессрочная серия остаётся бессрочной.
- Если recurrence_rule передан, это новое полное правило **для новой части**. Его COUNT не уменьшается дополнительно. Отсутствие COUNT/UNTIL означает бессрочное повторение.
- Исключения распределяются по original_start_at, а не по фактическому времени. Историческое занятие, перенесённое за границу, остаётся исключением исторической серии; результат предупреждает об этом. Будущее занятие, перенесённое назад, при preserve переходит в новую серию вместе со своим фактическим временем.
- При переносе времени всех будущих занятий preserve может оказаться невозможным: исходные начала больше не совпадают. В таком случае операция отклоняется; клиент должен явно выбрать discard либо сначала обработать исключения отдельно.

Результат содержит outcome, event_series_id, series (снимки и версии: сначала историческая часть, затем новая), changed_fields, discarded_exception_ids, transferred_exception_ids и warnings. Создание новой серии, изменение исторической и обработка исключений входят в одну транзакцию.

## Примеры аргументов

schedule_update_recurrence — понедельник и среда, с окончанием:

```json
{
  "event_series_id": "11111111-1111-1111-1111-111111111111",
  "expected_version": "<version из schedule_get>",
  "data": {
    "recurrence_rule": {
      "frequency": "weekly",
      "interval": 1,
      "by_weekday": ["MO", "WE"],
      "until": "2026-12-30T09:00:00+03:00"
    },
    "exception_policy": "reject"
  }
}
```

schedule_split_series — с выбранного занятия переносить оставшуюся часть на 12:00, наследуя оставшийся COUNT:

```json
{
  "event_series_id": "11111111-1111-1111-1111-111111111111",
  "expected_version": "<актуальная version>",
  "data": {
    "original_start_at": "2026-10-28T09:00:00+03:00",
    "start_at": "2026-10-28T12:00:00+03:00",
    "exception_policy": "reject"
  }
}
```

schedule_restore_occurrence:

```json
{
  "event_series_id": "11111111-1111-1111-1111-111111111111",
  "expected_version": "<актуальная version>",
  "original_start_at": "2026-10-28T09:00:00+03:00"
}
```

Восстановление удаляет исключение целиком: время, название и описание снова берутся из текущей серии. Если исключения нет, возвращается предупреждение. Общее правило серии не меняется. Сервис обновляет updated_at также при восстановлении через REST, чтобы старый токен не стал действительным после удаления исключения.

## Предпросмотр

schedule_preview_change принимает те же event_series_id, expected_version, data и дополнительно range_start/range_end. Наличие data.original_start_at выбирает split; без него выполняется предпросмотр update_recurrence.

Период положительный, не длиннее 366 дней; обязательны смещения. Ответ содержит before, after, proposed_events, список исключений для удаления/переноса и warnings. Он показывает только затронутую серию и её новые части, не весь календарь. Исключения проверяются по всей серии, в том числе за пределами выбранного окна.

Новая серия в предпросмотре имеет предварительный UUID; её ID и proposed versions нельзя использовать для записи. Для применения повторите data с исходным expected_version. Предпросмотр ничего не резервирует: если данные успели измениться, запись будет отклонена.

План строится в памяти. Рендеринг использует общую с обычным календарём функцию render_schedule и существующий generate_occurrences. Нет INSERT/UPDATE/DELETE и даже временных записей с последующим rollback. Сохраняются ограничения расчёта: не более 100000 проверенных повторений и 10000 экземпляров/исключений в выдаче.

## Время пользователя

get_user_context вызывается без аргументов и возвращает now_utc, local_datetime, local_date, timezone, timezone_mode, timezone_source, locale, week_starts_on=MO, time_format=24h и warnings. Имя, системный username и ID профиля не возвращаются.

В manual используется сохранённый IANA timezone. В system это последнее сохранённое браузером значение: сервер не может узнать текущую зону ОС MCP-клиента и явно сообщает это в warnings. Без профиля используется UTC с предупреждением. Поэтому MCP-клиент должен учитывать timezone_source и warnings, особенно если пользователь недавно сменил часовой пояс.

## Безопасность и проверки

Три инструмента записи имеют readOnlyHint=false, destructiveHint=true, idempotentHint=true: повтор тех же аргументов не повторяет изменение, но может вернуть конфликт. Preview и context имеют readOnlyHint=true, destructiveHint=false. openWorldHint=false для всех. Существующая защита localhost/Host/Origin сохранена.

Unit-тесты проверяют планы, COUNT, UNTIL, бессрочные серии, DST-пропуски, DTSTART и политики исключений. Интеграционные тесты запускают реальный MCP-клиент и проверяют разделение, восстановление, конфликты версий, параллельные вызовы, откат после flush, приватность контекста и совпадение preview с календарём. Отсутствие записей preview проверяется перехватом SQL и хэшем файла временной SQLite.
