# Безопасное редактирование календаря через MCP

Новые инструменты используют существующий CalendarService (в этом проекте он так называется), модели EventSeries/EventException и общую write_transaction. Политика версий и запрета изменения серий находится в CalendarEditingService, а MCP-обёртки только передают типизированные параметры и сериализуют ответы.

## Что добавлено в доменную логику

CalendarService уже предоставлял обновление/удаление событий, перенос, отмену и восстановление вхождений. Добавлены get_event_details с загрузкой правила и исключений и update_occurrence для частичного изменения времени, названия и описания одного вхождения. Последний использует существующий механизм move_occurrence и уникальный ключ (event_series_id, original_start_at), не создаёт отдельную серию и запрещает неявное восстановление отменённого вхождения.

Схема базы и REST-контракты не изменены. Поля title/description в EventException уже существовали и учитывались при построении расписания. null в этих полях означает наследование из серии; пустая строка description даёт пустое описание. Название не может быть пустым/null. Непереданные поля сохраняются.

## Последовательность работы

1. Найти event_series_id через schedule_list.
2. Вызвать schedule_get и получить полный event и непрозрачный version.
3. Передать эту строку как expected_version в инструмент записи.
4. Использовать version из успешного результата для следующего изменения либо снова вызвать schedule_get.

Version — SHA-256 канонического снимка события, правила и всех исключений, включая audit timestamps. Любое изменение снимка через MCP или REST делает прежнюю версию устаревшей. Это намеренно консервативная проверка: изменение другого вхождения той же серии также требует перечитать её.

Проверка выполняется после получения SQLite writer reservation в той же транзакции, что и запись. При двух конкурентных запросах с одной версией проходит только один. При ошибке все изменения откатываются. Миграция, отдельная колонка версии и журнал запросов для этого не нужны.

Повторная отправка уже выполненного запроса со старой версией даёт tool error с VERSION_CONFLICT и не выполняет действие второй раз. После удаления ID повторное удаление даёт ошибку отсутствия события. Это защита от повторного применения, а не кэш успешных ответов. После потери ответа сначала перечитайте состояние; не подставляйте новую версию для автоматического повтора без проверки результата.

## Инструменты

| Инструмент | Аргументы | Ограничения |
| --- | --- | --- |
| schedule_get | event_series_id | Возвращает EventDetails, правило, timezone, все исключения и version |
| schedule_update | event_series_id, expected_version, data | Только обычное событие: title, description, start_at, finish_at, timezone |
| schedule_reschedule | event_series_id, expected_version, start_at, finish_at? | Только обычное событие; без finish_at сохраняет фактическую длительность в UTC |
| schedule_update_occurrence | event_series_id, original_start_at, expected_version, data | Только повторяющаяся серия; title, description, start_at, finish_at одного вхождения |
| schedule_delete | event_series_id, expected_version, original_start_at? | Удаляет обычное событие либо отменяет одно вхождение серии; всю серию удалить нельзя |

Обычные события с ранее созданными REST-исключениями требуют отдельного разбора: новые инструменты отклоняют их изменение/удаление, чтобы не скрыть или не сбросить исключения.

Для повторного переноса вхождения всегда используйте его **исходное** время original_start_at, а не время после первого переноса. Чтобы изменить время вхождения, передавайте оба поля start_at и finish_at; при частичном обновлении неприсланное поле сохраняет прежнее значение. Изменение timezone всей серии недоступно. Для правил повторения теперь есть отдельные инструменты: [mcp-recurrence.md](mcp-recurrence.md).

Все входные моменты времени требуют UTC-смещения, выходные — UTC. timezone проверяется как IANA-имя. Длительность при schedule_reschedule сохраняется как разница UTC-моментов, включая переходы DST, а не как разница показаний настенных часов. До записи проверяется положительность итогового интервала.

## Пример

schedule_get:

```json
{"event_series_id": "11111111-1111-1111-1111-111111111111"}
```

schedule_update (подставить полученную строку version):

```json
{
  "event_series_id": "11111111-1111-1111-1111-111111111111",
  "expected_version": "<version из schedule_get>",
  "data": {"title": "Новое название", "description": null}
}
```

schedule_update_occurrence:

```json
{
  "event_series_id": "11111111-1111-1111-1111-111111111111",
  "original_start_at": "2026-10-26T09:00:00+03:00",
  "expected_version": "<актуальная version>",
  "data": {
    "title": "Индивидуальное занятие",
    "start_at": "2026-10-27T12:00:00+03:00",
    "finish_at": "2026-10-27T13:00:00+03:00"
  }
}
```

Результат записи содержит event_series_id, original_start_at (для вхождения), outcome, changed_fields, warnings, новую version и полный event. При физическом удалении event и version равны null. changed_fields отражает изменения полей события либо исключения; служебные timestamps не включены. Отмена меняет status исключения и убирает его временной интервал. Сохранение продолжительности отражается в warnings.

schedule_get имеет readOnlyHint=true, destructiveHint=false. Четыре инструмента изменения имеют readOnlyHint=false, destructiveHint=true, idempotentHint=true: повтор тех же аргументов не применяет изменение второй раз, хотя ответом может быть конфликт/отсутствие записи. openWorldHint=false. Аннотации не заменяют контроль доступа; используется прежняя политика localhost/Host/Origin сервера.

## Проверки

Тесты настоящего MCP-клиента покрывают переименование, перенос с сохранением длительности через DST, изменение/повторный перенос/отмену одного вхождения, сохранность остальных вхождений, запрет операций со всей серией, невалидные даты и зоны, конфликт после REST-изменения, конкурентные запросы и откат при сбое после flush. Все базы тестов временные.
