# Roadmap

План описывает последовательность продуктовых этапов, а не календарные сроки. Следующий этап начинается, когда предыдущий даёт устойчивую основу.

## Этап 1 — локальный планировщик

**Цель:** сделать приложение полезным без ИИ.

- Довести календарный backend и интерфейс до надёжных основных сценариев.
- Реализовано: независимый домен Task и Kanban-поток «Идеи → К выполнению → В работе → Готово», необязательные даты и приоритеты; см. tasks-api.md.
- Подключить HTML/JavaScript/CSS-интерфейс к FastAPI.
- Сохранять данные локально в SQLite; управлять схемой через Alembic.
- Применить палитру из `design-system.md`; учитывать интерфейсные референсы из `frontend/references/`.

**Готово, когда:** расписание и задачи можно использовать в повседневности, данные переживают перезапуск, а функции доступны без внешнего сервиса или модели.

## Этап 2 — подготовка расширяемости

**Цель:** укрепить границы модулей, прежде чем подключать интеллектуальные функции.

- Отделить правила календаря и задач от HTTP-слоя и интерфейса.
- Стабилизировать API и документировать доменные операции.
- Определить модель настроек, хранения секретов и разрешений для будущих интеграций.
- Уточнить потребность в экспорте, резервном копировании и восстановлении локальных данных.

**Готово, когда:** новые интеграции можно добавлять отдельными адаптерами, не меняя базовые сценарии и не создавая скрытую зависимость от сети.

## Этап 3 — модели и инструменты

**Цель:** добавить разговорный интерфейс как дополнительный способ работать с приложением.

- Выбрать первые локальные и/или облачные LLM-провайдеры.
- Реализовать адаптеры провайдеров за единым внутренним контрактом.
- Спроектировать набор инструментов для чтения и изменения календаря и задач.
- После этого выбрать роль и транспорт MCP для нужных сценариев.
- Установить явные правила подтверждения изменяющих операций и доступа к личным данным.

**Готово, когда:** пользователь может подключить выбранную модель, а её ошибки или отключение не ломают календарь и задачи.

## Этап 4 — личные знания

**Цель:** связать компаньона с пользовательскими заметками.

- Определить безопасный сценарий подключения Obsidian.
- Начать с ограниченного чтения выбранного хранилища; добавление и изменение заметок согласовать отдельно.
- Уточнить поиск, индексирование и обновление данных.

**Готово, когда:** пользователь контролирует доступные заметки, а чтение и запись не происходят неожиданно.

## Этап 5 — мир друга и компаньон

**Цель:** расширить приложение ролевым контекстом.

- Согласовать с автором мира API и формат базы знаний.
- Добавить поиск по лору и справочные страницы.
- Исследовать интерактивную карту и связь её объектов с материалами лора.
- Вернуться к чату-компаньону и персонажу-маскоту; определить визуальное поведение и объём анимации.

**Готово, когда:** материалы можно находить по содержанию, ответы опираются на согласованный источник лора, а карта помогает исследовать мир.

## Вне текущего плана

Пока не планируются как обязательства: публичный облачный сервис, многопользовательский режим, мобильные приложения, собственный хостинг языковой модели и замена LM Studio/Unsloth. Возвращаться к ним стоит только при изменении пользовательской цели.

## Открытые решения

- Каковы требования к резервному копированию и переносу локальных данных?
- Базовый объём задач определён и реализован: описание, приоритет, порядок, плановая дата, дедлайн и момент завершения. Проекты, теги и подзадачи остаются за пределами MVP.
- Какие LLM-провайдеры выбрать первыми и где хранить их ключи?
- Какие операции разрешать модели без подтверждения пользователя?
- В какой роли и топологии использовать MCP?
- Какой API и формат данных будет доступен для мира друга?
